The public API of Untrace Drive, version 1.

How it works, in three lines:

  1. Your code encrypts each file on your own machine with one standard step (AES-256-GCM, framed as UTE1, see "Client-side encryption" below).
  2. Drive receives ciphertext only and stores it across 6 regions; any 3 recover the file.
  3. On download, Drive returns the same ciphertext and the file key sealed to your key. Only your machine can unseal it. We cannot read your files.

Authentication is OAuth 2.0 client credentials: exchange your client id and client secret for a Bearer token that lasts 15 minutes.

Every operation is marked with x-status:

  • live: implemented on this version of Drive.
  • planned: part of the contract, not available yet. Calling it returns 404.

Errors always have the body { "error": "<code>", "message": "<text>" }.

Client credentials

A developer key is created in Drive (Settings, Developer keys) and shown once as a client id (utc_...) and a client secret (untrace_sk_v1_...). The secret never leaves your machine. Your code derives three values from it with HKDF-SHA256 (empty salt, 32 bytes each):

info label use
untrace:client-key:oauth:v1 the OAuth client_secret sent to the token endpoint (base64url, no padding)
untrace:client-key:box:v1 X25519 key pair; file keys are sealed to its public key
untrace:client-key:sign:v1 Ed25519 key pair; identifies the key

Because only the derived OAuth value travels, Drive can never compute the box key, so it can never open a file key sealed to you.

Client-side encryption (UTE1)

Each file gets a fresh random 32-byte file key. The plaintext is sealed with AES-256-GCM in chunks:

header (17 bytes)
  [0..3]   "UTE1" (ASCII)
  [4]      version, 0x01
  [5..8]   chunk size in plaintext bytes, uint32 big-endian, 1..16777216
  [9..16]  total plaintext length, uint64 big-endian
then, for chunk i = 0, 1, ... (ceil(total / chunk size) chunks):
  12-byte random IV | ciphertext | 16-byte GCM tag
  additional authenticated data = header (17 bytes) || i as uint32 big-endian

The header fixes the exact length of the body, so a truncated or padded body is refused. Never reuse an IV with the same file key.

Sealed keys

A sealed key is the 32-byte file key sealed to an X25519 public key: base64(ephemeral public key (32) || nonce (24) || XSalsa20-Poly1305 box (48)), the NaCl box construction with a fresh ephemeral key pair per seal.

On upload you send two sealed keys: one to your own box public key, and one to the Drive owner's sharing key (GET /api/v1/owner/share-key, verify its signature first). Drive stores sealed keys only.

Auth

OAuth 2.0 client credentials.

POST /api/v1/oauth/token Live

Exchange client credentials for a Bearer token

OAuth 2.0 client credentials grant (RFC 6749 section 4.4). Send the client id and the derived OAuth client secret (see "Client credentials"), either in the form body or as HTTP Basic auth. The token lasts 15 minutes; get a new one when a call answers 401 token_expired.

The account that owns the key needs an active plan: without one this returns 402 payment_required.

No Bearer token: this call authenticates with your client credentials.
